# Cloud Run 上で動かすときのノウハウ

TiledFlipperServer をクラウドのコンテナ実行環境 (Cloud Run) に置いたときに
効いてくる制約と、その回避策をまとめたもの。

関連するドキュメント。

- `../RunningLocally.md` — 手元での起動と終了
- `Concurrency.md` — 多重アクセスとタスクモデル
- `ServiceDesign.md` — gRPC サービスの設計

このリポジトリはデモンストレーションであり、クラウドでのコンテナ運用に
求められる要件をひととおり満たしてはいない。ここは「いま何がどうなって
いるか」の記録であって、本番運用の手引きではない。

なお、実際にデプロイしたサービスの URL はここには書かない。デモ用の
エンドポイントは今後公開される可能性があるため、接続先は
`TiledFlipperEndpoint.local.txt` (git 管理外) 側だけで持つ。

## スケールの単位はインスタンス

Cloud Run はコンテナの中のプロセスを勝手に増やさない。スケールの単位は
**コンテナインスタンス** であり、

    1 インスタンス = 1 コンテナ = このプログラム 1 プロセス

という対応になっている。負荷が増えたときに増えるのはプロセスではなく
インスタンスのほうで、そのインスタンスの中では 1 プロセスが複数の
リクエストを受け持つ (`Concurrency.md` を参照)。

## 同時実行数 (concurrency)

「同じプロセス内に何件まで相乗りさせるか」は Cloud Run の同時実行数で
決まる。プロセスを分けたいか集約したいかは、この値の選び方の問題になる。

```sh
# 1 インスタンスあたりの同時リクエスト数を指定する
gcloud run services update <サービス名> --concurrency=80
```

| 設定 | 効果 |
| --- | --- |
| `--concurrency=80` | 既定値。1 プロセスに最大 80 リクエストが相乗りする。 |
| `--concurrency=1` | 1 インスタンスあたり 1 リクエスト。実質「アクセスごとに別プロセス」に近い分離になるが、コストは大きく上がる。 |
| `--concurrency=<n>` | 最大 1000。上げるほど 1 プロセスへの集約が進む。 |
| `--min-instances=1 --max-instances=1` | インスタンスを 1 つに固定する。全アクセスが確実に同じプロセスへ集まる。 |

既定のまま置けば、すでに 1 プロセスへ最大 80 件が集約されている。

## 待ち受けアドレスと `PORT`

`main.swift` の既定は `127.0.0.1:31415` で、`PORT` 環境変数は読んでいない。
Cloud Run はコンテナが `0.0.0.0:$PORT` (既定 8080) で待ち受けることを
要求するので、デプロイするイメージ側で

```sh
TiledFlipperServer --host 0.0.0.0 --port 8080
```

のように必ず引数で渡すこと。継続的に運用するなら、`PORT` が設定されて
いればそれを使うフォールバックを `main.swift` に足しておくと事故が減る。

## HTTP/2 (h2c)

トランスポートは平文の HTTP/2。gRPC を通すにはサービス側で HTTP/2 の
エンドツーエンド (`--use-http2`) が有効になっている必要がある。

外部からの通信は Cloud Run の前段が TLS を終端するので HTTPS になる。
手元のテストサーバーは平文のままなので、本物のトークンを流さないこと。

## リクエストタイムアウトと、終端の無いストリーム

`TileFlipService.flips` は差し替え指示を流し続けるサーバーストリーミングで、
クライアントが読むのをやめるまで終わらない。ここが Cloud Run と噛み合わない。

- Cloud Run は処理中のストリームを同時実行数の 1 枠として数え続けるため、
  繋いだクライアントは切断するまで枠を占有する。
- リクエストタイムアウト (既定 300 秒、最大 3600 秒) に達すると、サーバー側
  から強制的に切られる。

長く流し続けたいなら、タイムアウトを延ばすか、クライアント側に再接続を
用意する必要がある。ストリームが切れて張り直されると、サーバー側が抱えて
いた一時的な状態や参照は無効になるので、後始末を `defer` に置いておくこと。

## ルーティングはリクエスト単位

`Concurrency.md` に書いたとおり、いまのサーバーは RPC をまたいで持ち越す
状態を持たない。そのため水平スケールは安全だが、**RPC 間で状態を共有する
機能を足すとこの性質が壊れる**。

`flips` のストリームを保持しているインスタンスと、あとから来た
`getDescriptions` が到達するインスタンスは、別とは限らないどころか別に
なり得る。Cloud Run のルーティングは接続単位ではなくリクエスト単位で、
同じ HTTP/2 接続の上の別ストリームが別インスタンスへ振られることがある。
プロセス内の actor に置いた共有状態は、その場合に黙って空振りする。

回避策は 3 つ。デモの範囲なら 1 番目。

1. `--max-instances=1` (と `--min-instances=1`) でインスタンスを 1 つに
   固定する。デモとしては十分だが、当然スケールしない。
2. Cloud Run のセッションアフィニティを使う。ただし Cookie ベースの
   ベストエフォートで、gRPC には噛み合わない。
3. 外部のブローカー (Memorystore/Redis の Pub/Sub、Cloud Pub/Sub、Firestore の
   リスナー) を経由させる。インスタンスをまたいで通知が届く唯一まともな方法
   だが、依存が一気に増える。

そもそもこの壁を避ける手もある。`ServiceDesign.md` の双方向ストリーミングに
すると、両方向が同じストリーム = 同じタスク = 同じインスタンスに閉じるので、
共有状態そのものが要らなくなる。

## ファイルシステムはメモリ

**ここは誤解しやすい。** Cloud Run のコンテナファイルシステムは書き込み可能
だが、実体はインメモリファイルシステム (tmpfs)。`/tmp` に 500 MB 書けば、
インスタンスのメモリを 500 MB 消費する。

つまり「メモリに溜め続ける代わりにストレージへ逃がす」という判断は、
Cloud Run 上では効果が無い。むしろ `Data` で持つよりコピーが増えるぶん
不利になることさえある。書いた内容はインスタンス停止時に消え、永続もしない。

さらに同時実行数と掛け算になる。既定では **最悪ケースが「1 ストリームあたり
の最大サイズ × 80」** としてメモリに乗る。ここを見積もらずに実装すると
OOM でインスタンスごと落ち、1 本のストリームの暴走が同居している 79 本を
巻き添えにする。

### 大きなバイナリを受けるときの選択肢

**(a) tmpfs で割り切る。** 1 ストリームあたりの上限を明示的に決められるなら
これが一番簡単。`--memory` を上げ、上限超過は
`RPCError(code: .resourceExhausted)` で弾く。デモならこれで十分。

**(b) Cloud Storage を FUSE でボリュームマウントする。** Cloud Run はバケット
をボリュームとしてマウントできる (第 2 世代実行環境が必要)。書き込みが実際に
GCS へ行くのでメモリを食わない。ただし POSIX ファイルシステムではないので
追記や部分書き込みは苦手で、ファイルが見えるのは close 後。「パーツを順に
追記していく」用途とは相性がよくない。

**(c) GCS へ直接ストリーミングアップロードする。** 素直な解。受け取った
パーツを resumable upload に流せば、メモリにもディスクにも溜めない。GCS には
compose API があり、分割して置いたオブジェクトをサーバー側で結合できる
(1 回 32 個まで、再帰可)。

ただし **Swift 用の公式 Google Cloud クライアントは無い**。REST API を自分で
叩き、メタデータサーバー (`metadata.google.internal`) からアクセストークンを
取る実装を書くことになる。手間を避けるなら、署名付き URL を gRPC で発行して
アプリから直接 GCS へ上げさせ、サーバーはオブジェクト名だけ受け取る、という
分担が現実的。

一時領域を RPC ごとに分ける方法は `Concurrency.md` の「Task ごとの一時領域を
分ける」を参照。

## IAM 認証と `Authorization` ヘッダーの衝突

Cloud Run の IAM 認証 (`--no-allow-unauthenticated`) と、アプリ自前の
ユーザー認証は、**どちらも同じ `Authorization` ヘッダーを使う**。

| | 中身 | 識別できるもの |
| --- | --- | --- |
| Cloud Run の IAM 認証 | Google 発行の ID トークン | 呼び出し元プリンシパル (サービスアカウント等) |
| アプリ自前の認証 (Firebase Auth / Sign in with Apple など) | 自前または IdP 発行の JWT | アプリのエンドユーザー |

前者は「誰がこのサービスを叩いてよいか」の話で、アプリのユーザー個人を
表さない。iOS アプリのユーザーを判別したいなら後者になる。

そしてヘッダーは 1 つしか無い。IAM 認証を有効にしたまま自前のユーザー
トークンも送りたい場合、`Authorization` は Cloud Run 用の ID トークンで
埋まる。定番の回避は、自前のトークンを `x-user-authorization` のような別の
メタデータキーに載せること。gRPC のメタデータは任意のキーを足せるので手間は
かからない。

サーバー側での読み取り方は `ServiceDesign.md` を参照。

## デモとして踏み込んでいない点

このリポジトリで手当てしていない、本番運用なら必要になるもの。

- 認証・認可 (いまは未認証で誰でも呼べる前提)
- 1 クライアントあたりの接続時間やストリーム数の制限
- ヘルスチェックとグレースフルシャットダウン (SIGTERM の受け止め)
- 構造化ログとリクエストの追跡
- 配布するコレクション一覧の実行時更新 (いまは起動時に固定)
