# Claude Code の `ScheduleWakeup` / `/loop` について分かったこと

コンテナのビルド (数分かかることがある) や Cloud Build のような、完了まで
待つ必要がある作業を Claude Code (このリポジトリでの作業を進めている
AI エージェント) にやらせる際に使った `ScheduleWakeup` と `/loop` の
挙動について、実際に分かったことをまとめる。TiledFlipperServer 自体の
話ではなく、開発を進める上での運用ノウハウ。

## それぞれの役割

- **バックグラウンドコマンドの完了通知**: `container build` や
  `gcloud builds submit` のような時間のかかるコマンドをバックグラウンドで
  実行すると、完了時に `<task-notification>` という形で自動的に知らせが
  届く。**これは今まで 100% 確実に届いていた。**
- **`ScheduleWakeup`**: 「N 秒後にもう一度この内容で自分を起こす」という
  予約を行うツール。本来は `/loop` のダイナミックモード (間隔を指定しない
  `/loop`) 専用の仕組みで、上記の「バックグラウンドコマンドの完了通知」を
  受け取れない、もっと長時間・不定期な監視 (外部サービスのログを定期的に
  見に行く等) のために用意されている。
- **`/loop` ダイナミックモード**: `/loop <やりたいこと>` のように間隔を
  指定せずに呼び出すと、その場でタスクを実行した後、`ScheduleWakeup` で
  自分の続きを予約し、以後は自己ペースで繰り返す。

## 分かったこと: VSCode 拡張機能上では自動発火が信頼できない

`container build` や `gcloud builds submit` の完了を待つ際、当初
`ScheduleWakeup` を使って「N 分後に確認します」と予約していたが、
**予約した時間になっても自動では何も起きず、結局ユーザーが「状況を
確認して下さい」と手動で入力することで会話が先に進む、という状態が
何度も続いた。**

一度だけ、システム側からの `/loop` コマンド呼び出しとして自動的に
再開した瞬間があった (ユーザーの入力ではなく `<command-message>loop</command-message>`
という形式で来た) ので、仕組みとして完全に動かないわけではないが、
**自動発火の信頼性は低い。**

考えられる原因:

- Claude Code が VSCode の拡張機能ホストの中で動いているため、
  ウィンドウが非アクティブになる等でホストの活動が OS/VSCode 側から
  抑制され、タイマー処理が遅延・停止する
- 独立したターミナル (Terminal.app 等) で直接 CLI を動かす場合は、
  この抑制を受けにくいと考えられるが、実際に比較検証はしていない

## 成功パターン: `/loop` + バックグラウンドタスクの完了通知でコンテナビルドを待つ

上記の「手動で `ScheduleWakeup` をポーリング的に使う」失敗パターンとは別に、
正式に `/loop` スキル (間隔指定なし、ダイナミックモード) 経由で
`Server/Tools/run-in-container.sh` の完了を待たせる形を何度か試したところ、
**3 回とも問題なく完了まで到達できた。** やったことは:

1. `/loop <ビルド・起動・疎通確認までまとめてやってほしい内容>` の形でスキルを呼び出す
2. スキルの指示通り、その場でビルドスクリプトをバックグラウンド実行する
3. **Monitor は立てない。** `Bash` の `run_in_background` で起動したコマンドは
   それ自体が完了時に `<task-notification>` を自動で送ってくるので、
   スキルが言う「イベント待ちなら Monitor を立てる」の対象にはならない
4. `ScheduleWakeup` は「本当に間に合わなかったときの保険」として、想定より
   長め (240 秒 〜 20 分など) の値で一度だけ予約する
5. 実際にはどのケースも、予約したフォールバックの時間が来るより先に
   バックグラウンドタスク自身の完了通知が届き、それをきっかけに
   `ScheduleWakeup({stop: true})` でループを閉じて結果を報告した

試した内容と結果:

| ケース | 結果 |
|---|---|
| 2 CPU/4GB, swift:6.2 でビルド・起動・疎通確認 | 成功。タスク自身の通知で完了、フォールバック (4分) は未発火 |
| コンテナの停止のみ | その場で即完了。次のイベントが無いのでそもそも `ScheduleWakeup` を呼ばずにループ終了 |
| 2 CPU/2GB (メモリ最小構成) でビルド・起動・疎通確認 | 成功。フォールバックを 20 分に長めに取ったが、実際は数分でタスク自身の通知が届いた |

**教訓**: `ScheduleWakeup` のフォールバック時間は「ちょうど良い値」を
狙う必要が無い。バックグラウンドタスクの完了通知の方が先に届く前提で、
むしろ余裕を持って長め (数分〜数十分) に設定しておけば、フォールバックが
発火する前にタスク通知で片が付く。**ただしこれは「タスク自身が完了通知を
出してくれる場合」に限った話で、`ScheduleWakeup` 自身のタイマーが
VSCode 拡張機能上で自律的に発火するかどうかという、上で書いた根本の
疑問への答えにはなっていない。** 今回の 3 回とも、フォールバックの
`ScheduleWakeup` が実際に発火する前にタスク通知が先着したため、
「予約した時間になっても何も起きない」問題が起きる余地自体が無かった。

ビルダー VM の再作成 (`container builder delete --force` /
`container builder start`) がハングした場面が今回も一度あったが、これは
`/loop` や `ScheduleWakeup` の問題ではなく、Apple Container 側の別の
既知の不具合 (AppleContainer.md の「2. ネストされた runc がまれに
デッドロックする」) で、VM プロセスを直接 kill して復旧するという
従来通りの手順で対応した。

## 運用上の結論

1. **バックグラウンドコマンドの完了を待つだけなら `ScheduleWakeup` は
   使わない。** 完了通知が自動で届くので、それを待てば十分。
   `ScheduleWakeup` を重ねて「ポーリング」するのは二度手間になる上、
   前述の通り自動発火が信頼できないため、かえって「予約したのに
   反応が無い」という体験になりやすい。
2. **`/loop` のダイナミックモードを使うなら、本当に長時間・不定期な
   監視が必要な場面に限る。** 数分待てば終わるビルドの完了待ちには
   不向き。
3. **確実に無人で定時実行したい場合は `/schedule` (クラウドスケジュール)
   を使う。** これは Anthropic のクラウド側で動くため、ローカルの
   VSCode セッションが起動しているかどうかに依存しない。
4. macOS 自体を常時起動したままにしておく運用であれば「Mac のスリープで
   タイマーが止まる」という懸念は無くなるが、VSCode 拡張機能ホストの
   抑制という別の要因が残る可能性がある。この点を切り分けたいなら、
   独立したターミナルで Claude Code CLI を動かして比較するのが良い
   (未検証)。
